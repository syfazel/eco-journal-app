## The blocker, precisely (so it is not retried blindly)

Every Gradle invocation fails the same way, after the daemon
starts cleanly:

```
FAILURE: Build failed with an exception.
* What went wrong:
Could not receive a message from the daemon.
  DaemonConnectionException at DaemonClientConnection.receive
  (no underlying cause — the daemon closed the connection
  without sending a reply)
```

Client-side `--debug` trace (2026-10-25): daemon starts, binds
(e.g. `127.0.0.1:43835`), greeting pipe works, client TCP
connects, client dispatches the `Build` message — and 25 ms
later the receive fails. The daemon's own log shows NO incoming
connection at all and exits normally when the client removes it
from the registry. Heap size is NOT the cause (fails identically
at `-Xmx2048m` and `-Xmx1024m`; plain `java -Xmx2048m -version`
works).

Minimal reproduction of the underlying cause:

- Python → Python over `127.0.0.1`: WORKS (real bytes arrive).
- Java → Python over `127.0.0.1`: the sandbox answers INSTEAD
  of the real server with: "Other TCP connections is turned off
  for this assistant. To allow it, ask the user to open Muse
  settings -> Permissions -> Direct network protocols and switch
  other_tcp from Deny to Ask." (With
  `-Djava.net.preferIPv4Stack=true` the connect reaches the
  server but the read then fails with `Connection reset`.)
- Therefore: JVM loopback TCP is intercepted/broken in this
  sandbox, while native loopback works. Gradle's daemon protocol
  is JVM→JVM loopback TCP, so no Gradle build can run here,
  regardless of JDK/Gradle version, heap, or daemon flags tried
  (`--no-daemon`, `--foreground`, `GradleMain`, smaller heap —
  all fail identically).

What would unblock a local build (a decision for Yasin/parent,
NOT done here): changing that Muse network permission
(`other_tcp` from Deny to Ask) — or accepting that local builds
do not run in this sandbox at all. Phase 3 deliberately did NOT
ask Yasin to change any security setting; the cloud-build route
below needs no such change.

## Update 2026-10-25 ~18:56 Tehran — First build under Ask mode FAILED

Yasin turned Other TCP on (Ask) at ~18:47. The first local build
(`assembleDebug --no-daemon`, Gradle 8.7 local) forked a single-use
daemon, which needed a loopback connection to 127.0.0.1:45181.
The approval card for that connection was decided "Site always
allowed" at 18:56:27, but the build still failed with
`DaemonInitialConnectException: The first result from the daemon
was empty` (GRADLE_EXIT=1, no APK, no app/build/ output). Likely
cause: the single-use daemon died while waiting for the approval,
or the approved port does not carry over to the next daemon run
(daemon ports are random per run). A second attempt was launched
immediately afterwards WITHOUT --no-daemon, so a persistent daemon
can survive the approval wait and be reused.

## Update 2026-10-25 ~18:58 Tehran — Second build under Ask mode ALSO FAILED

Second attempt (persistent daemon, no --no-daemon) failed the same
way at the daemon-connect stage: `NoUsableDaemonFoundException:
A new daemon was started but could not be connected to`
(pid 10850, port 38891, state Busy; GRADLE_EXIT=1, no APK).
The approval card for 127.0.0.1:38891 was decided "Site always
allowed" at 18:57:49 (29s after request), yet the client still
could not connect, and afterwards `gradle --status` shows both
daemons STOPPED. Conclusion from two approved attempts: Ask +
per-port approval does NOT make JVM loopback work for the Gradle
daemon protocol in this sandbox — the connection is intercepted
and never delivers a usable daemon handshake, regardless of
single-use vs persistent daemon. Local builds should NOT be
retried again without a different mechanism. The remaining route
to a first APK is the GitHub Actions cloud build (Route B),
which needs only the one-time repo push.
